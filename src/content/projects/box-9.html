Flowcharts, Code Iterations & Test Data

Both challenges were solved the same way: define the logic as a flowchart, code it, run it, read what went wrong, and change exactly one variable at a time until it worked.

May 30 — Problem Definition

Two Challenges, Two Boards

The Warehouse Challenge board is a winding black line squeezed between orange cone obstacles with very little clearance — the robot has to follow the line accurately or it clips a cone. The Parallel Parking board is a marked start box facing two blue box "cars" the robot has to slide between without contact. Both problems and their pass/fail questions were written out before any code was touched.

May 30 – June 1 — Flowcharts

Mapping the Logic Before Writing Code

The Warehouse flowchart is a simple decision loop: the light sensor checks for the black line — if detected, both drive motors run; if not, the robot reverses for 0.5 seconds and executes a 360° point turn to reacquire the line. The Parallel Parking flowchart is a state sequence: detect the wall and drive forward, stop once the wall is no longer detected, complete a 90° swing turn, move forward, then complete a second swing turn to settle parallel to the box.

June 1 — Process for the Code (Warehouse)

Five Versions to Tune the Line Sensor

First guess was to drop the light-sensor threshold from 45 to 25, on the theory that a lower value would be more sensitive to the darker line — that turned out to be backwards, and the robot ran too fast and shot off the line. Reverting the sensor value to 45 and instead cutting drive motor power (60% → 40% → 20% across V2–V5) was what actually fixed it: the sensor logic was already correct, the robot just needed to be slow enough to react to it.

Key correction: "Reason V2" in the notebook explicitly flags Reason V1 as false — a documented example of catching your own wrong hypothesis mid-project.

June 1 — Process for the Code (Parallel) & Manufacturing

Distance Tuning, Motor Asymmetry & Sensor Placement

The parking code went through five versions: setting the sonar trigger distance to 23 cm (the measured distance from the wall at box-center), reversing motor polarity and extending the wait time when the robot undershot its backward move, adding a forward creep plus final turn sequence to square up in the box, then two rounds of shortening/rebalancing that final turn (500ms→1000ms wait, 100%→60% power on motor C) after it kept over-rotating. On the hardware side, a light sensor was added to the back of the chassis and then re-mounted closer to the ground after it failed to reliably detect the line; two sonar distance sensors were added front-left and front-right — one for parking, the second purely to balance the robot's weight.

May 31 – June 1 — Testing Data & Description

Mistake: Six Failed Parking Attempts Before Test 7

The Warehouse test log shows 4 of 5 runs succeeding in 44–50 seconds, with one early failure (V1's backwards sensor logic) and one run that finished despite a wheel falling off near the end. The Parallel Parking log is rougher: tests 1–6 each failed a different way — starting backward instead of forward, running straight into the first box and getting stuck, popping a wheel off mid-turn, or landing in the zone without being parallel and clipping the box anyway. Only on test 7, after rebalancing motor C's final-turn power down to 60%, did the robot park cleanly.

Lesson learned: six back-to-back failures didn't mean the approach was wrong — each failed test isolated a different single variable (direction, wait time, turn power) to fix next, which is what eventually converged on a working sequence.

June 6 — Analyze & Conclusion

Tying Results Back to the Original Questions

For the Warehouse Challenge, the robot avoided the obstacles and finished the course in 4 of 5 runs — comfortably clearing the "50% of the time" bar from the original question. For Parallel Parking, the single clean run on test 7 was enough to satisfy the stricter "without hitting the boxes once" requirement. Both write-ups explicitly reference the test data tables and trace the fix (motor power for the line follower, final-turn power for parking) back to the specific problem it solved.

Mistakes & What They Taught Me

Wrong First Hypothesis

Assumed a lower light-sensor threshold would fix line detection; it didn't — the robot was just moving too fast to react. Logged the wrong guess and the correction openly instead of erasing it, which made the real fix (motor power) easier to justify.

Sensor Placement

The first light sensor mount didn't reliably see the black line at all. Moving it physically closer to the ground — a hardware fix, not a code fix — solved what looked at first like a software bug.

One Variable at a Time

Six straight parking failures each isolated a single cause — direction, wait time, or turn power — rather than changing everything at once. That discipline is what made test 7 the first clean run instead of a lucky one.

Final Results Reference

Warehouse Challenge: 4 of 5 runs completed successfully at 44–50 seconds each, meeting the "50% of the time" target with room to spare. Parallel Parking Challenge: 7 attempts logged, with the robot contacting a box on 2 of the first 6; test 7 completed the course with zero contact, meeting the "not once" requirement on the strength of that single clean run.
